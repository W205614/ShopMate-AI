# AI 质量验证

本流程面向校招展示与本机使用。协议契约、真实模型任务结果与人工评分分别保存，不能由假模型通过推导真实用户准确率。

## 两套问题

- `contract`：原有 40 条知识、事实、澄清、安全及确认操作契约；无付费 `matrix` 模式进入 CI，真实 `live` 模式保留原有 12 条代表场景。
- `holdout`：独立维护的 12 条任务问题，覆盖两商品比较、预算推荐依据、只问材质、口语价格、只补售后原因、只补规格数量、政策例外、工作日、未知商品、越权要求、本人订单及条件运费。题目和期望不由协议假服务导入。它是与原契约分开的固定评测集，经过维护后应视为回归集，不宣称盲测或真实用户总体样本。

两套均经 HTTP、检索、工具、任务与持久化运行。真实模式的模型、Embedding、Reranker 全部经过同项目认证代理；代理在外部调用前把次数写入宿主账本，失败也占用额度。`AI_ACCEPTANCE_MAX_REQUESTS` 可下调上限，默认 100、绝不超过 100；时限仍为首次调用起 20 分钟。重跑必须复用原账本与 token，不得换目录重置额度。达到上限应报告未完成项。

## 隔离运行

沿用 [既有复跑方法](final-acceptance-20261021.md#复跑与交付边界) 创建独立项目、端口、空卷和凭据。禁止日常 18086 入口及日常卷。免费矩阵使用 `compose.quality.yaml`；获准的真实模型使用 `compose.quality-live.yaml`。选择新问题集时，给运行器增加：

```powershell
$env:AI_QUALITY_SUITE = 'holdout'
$env:AI_ACCEPTANCE_REPORT = '.delivery/quality-holdout-initial.json'
node backend/scripts/ai-quality.mjs
```

网关创建前设置 `$env:AI_ACCEPTANCE_MAX_REQUESTS = '60'` 可将本轮上限降至 60。这不是费用承诺，各类调用仍按供应商计费。修复后可用 `AI_QUALITY_CASE_IDS` 定向复测，使用新的报告名，保留初跑及全部失败记录，不将累计覆盖冒充一次整组通过。

## 结果与人工复核

JSON 报告保存相关源码及评测脚本 SHA-256、原问题、原答复、引用、断言、耗时、工具和模型调用、降级及持久预算。`answerable` 是预先标注可回答的题数；`resolvedAnswerable` 仅计任务完成、全部断言通过且未降级的题；`falseRefusals` 计这些题中返回 `handoff` 的次数。解决率与误拒答率共用该分母，分母为零返回 `null`。执行失败、格式失败、检索降级、安全拒绝独立列出，不当作正常成功。

同时生成 `.human-review.json`，默认 `pending_human_review`，各评分为空。人工按事实与引用、切题程度、建议或追问有效性各 0–2 分填写，并记录评审人及理由。自动断言不能填成人工评分，也不能用只出现正确数字就认定整段回答正确。人工尤其检查推荐是否符合需求、比较是否有助选择、摘录是否遗漏跨句条件，以及本应回答的问题是否被拒绝。

固定样例仍不能证明真实用户准确率。后续有真实使用记录时，先获准并脱敏，再加入与开发回归问题分离的样本；不要上传真实账号、地址、会话或密钥作为评测夹具。
