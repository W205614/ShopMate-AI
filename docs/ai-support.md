# AI 客服与知识库

AI 功能在现有 Node.js／Express、Vue 和 SQLite 服务内运行，仍使用 API、Web 两个容器。配置示例默认 `AI_ENABLED=false`，此时会话使用 FAQ 规则和人工回复。开启后，用户消息先入库并排队，页面显示处理阶段，完成后展示整段回答、来源及确认卡片；没有逐字流式输出。

本文说明实现、配置与操作方法，不代表供应商可用性、回答准确率或本轮部署验收结果。历史电商及负载验收仍保留在各自报告中。

## 模型配置

从仓库根目录的 `.env.example` 复制缺少的配置到被 Git 忽略的 `.env`，保留原管理员、访问源、端口和备份配置。全部凭据仅供后端使用，不使用 `VITE_` 前缀，不提交 `.env`，不在排障输出中打印完整环境变量。

| 配置 | 默认值与用途 |
| --- | --- |
| `AI_ENABLED` | `false`；设为 `true` 开启 AI 对话 |
| `LLM_BASE_URL` | `https://api.deepseek.com`；后端在其后拼接 `chat/completions` |
| `LLM_MODEL_ID` | `deepseek-flash`；对话、工具调用及图片转录共用，账号需有相应模型访问权限 |
| `LLM_API_KEY` | 必填的模型服务 Key |
| `AI_PROVIDER_TIMEOUT_MS` | `30000`；单次对话／Embedding 请求超时，允许 100–90000 ms |
| `AI_MAX_CONCURRENT` | `2`；全局同时处理会话数，允许 1–8 |
| `AI_MAX_QUEUE` | `20`；除并发处理数外的排队容量，允许 1–100 |
| `AI_USER_DAILY_CONSULTATIONS` | `20`；每账号每日 AI 咨询数，失败任务重试也占一次，允许 1–10000 |
| `AI_DAILY_PROVIDER_CALLS` | `100`；全局每日对话、Embedding、重排和视觉请求数，允许 1–100000 |
| `SUPPORT_DAILY_CONVERSATIONS` | `20`；每账号每日新建会话数，允许 1–1000 |
| `SUPPORT_MAX_USER_TURNS` | `100`；每会话用户消息轮次上限，允许 1–1000 |
| `AI_KNOWLEDGE_MAX_CHUNKS` | `5000`；全库索引分段上限，包含草稿及保留版本，允许 1–100000 |
| `AI_KNOWLEDGE_MAX_VECTOR_BYTES` | `67108864`（64 MiB）；全库向量字节上限，允许 1–268435456 |
| `EMBEDDING_BASE_URL` | 填写供应商的 OpenAI 兼容 API 基址，例如服务要求的 `/v1` 基址；后端拼接 `embeddings` |
| `EMBEDDING_API_KEY` | 文档索引及向量检索使用的 Key |
| `EMBEDDING_MODEL` | `text-embedding-3-large` |
| `EMBEDDING_DIMENSION` | `3072`；返回向量长度必须与之匹配，且各元素有限、向量非零 |
| `SEND_EMBEDDING_DIMENSIONS` | 示例与 Compose 为 `false`；不向不兼容该参数的代理传 `dimensions`，仍校验实际返回长度 |
| `RERANKER_ENABLED` | `true`；可设为 `false`，检索会标明使用融合排序降级 |
| `RERANKER_URL` | `https://api.siliconflow.cn/v1/rerank`；也可填写兼容服务的基址 |
| `RERANKER_API_KEY` | 重排服务 Key |
| `RERANKER_MODEL` | `Pro/BAAI/bge-reranker-v2-m3` |
| `RERANKER_TIMEOUT_SECONDS` | `2`；独立重排请求超时，允许 1–30 s |

完整文档检索需配置对话与 Embedding；Reranker 不可用时可降级。仅使用商品／订单工具和 FAQ 时，不需要先上传文档。`AI_ENABLED` 控制客服对话，文档上传后的处理任务独立运行，仍可能调用 Embedding 或视觉模型。

数值配置仅在未设置时使用默认值；非法值、非整数或越界值会在启动时明确报错。`0` 不是停用额度的方式，关闭对话使用 `AI_ENABLED=false`。文档任务的 `AI_PROVIDER_BUDGET_EXHAUSTED` 表示当日额度耗尽；`AI_PROVIDER_BUDGET_UNAVAILABLE` 表示额度数据库或进程通信不可用，应先检查服务状态。

修改 `.env` 后，在根目录执行：

```powershell
docker compose up -d --build --wait
docker compose ps
```

源码开发脚本自动读取根目录 `.env`，重新启动后端以应用修改。Docker 镜像已含 Poppler；本地运行 PDF 功能的额外前提见 [开发文档](development.md#本地开发)。改 Embedding 模型或维度后，现有向量不会自动变成新模型的向量：编辑保存正文，完成重新索引并发布；未匹配的新模型向量仅使用关键词结果并显示降级。

## 第一次体验

1. 先按 [README](../README.md#快速部署) 部署，注册普通用户。商品和本人订单都可作为咨询上下文，订单查询只允许当前登录账号。
2. 启用 AI 后发送商品或订单问题，观察排队、查询、检索和生成阶段。活跃 AI 任务、等待人工或人工服务期间会轮询当前会话；空闲机器人会话不轮询，关闭会话或离开页面后停止。刷新会重新读取已入库状态。
3. 需要加购时明确商品规格与数量；取消订单或申请售后时明确目标订单与明细。核对卡片内容后点击确认，或取消提案。未点击确认前业务数据不变。
4. 管理员或具有客服权限的员工进入“知识库”，维护 FAQ 或上传面向顾客的文档。等待处理结束后打开预览，重点核对金额、日期、单位、否定词及复杂表格，再手动发布。
5. 用户询问文档覆盖的问题，展开来源查看标题、页码或段落和摘录；无法确定时补充问题或转人工。人工工作台继续提供回复与关闭会话。

普通会话支持多轮追问，每轮最多使用当前消息及此前 12 条消息作为模型上下文。刷新后可恢复已提交消息、任务和提案；未发送的输入草稿只保留在当前页面内存中。

模型最终结果分为澄清（`clarify`）、事实答复（`grounded`）与转人工（`handoff`）。澄清与转人工使用服务端固定文案；事实正文由服务端从当前商品、本人订单、售后和待确认提案生成，政策展示仍有效的已发布资料摘录。模型自由文本不直接展示为业务承诺。旧协议未提供 `replyKind` 时按事实答复处理，仍必须经过相同证据选择与服务端生成，没有证据则返回无法确认。来源有效不等于内容一定正确，发布人员仍须审核资料并抽检引用是否支持提问。

每日额度按北京时间（`Asia/Shanghai`）切日，使用数据库账本，重启不重置；新部署的账本从首次使用开始计数。外部请求在发起前用短事务占用全局额度，失败请求也计入，网络等待不持有写事务；文档子进程先通过 IPC 向主进程申请额度。超额不发出新的供应商请求，用户可转人工或次日再试。消息和幂等结果仍保留；重复重放已完成业务请求不重复扣次数。独立40条协议验收使用 `compose.quality.yaml` 中200次咨询／2000次服务请求额度；真实模型验收另外受原有代理100次／20分钟预算约束。

## 知识上传、版本与检索

| 格式 | 处理方式 |
| --- | --- |
| TXT、MD、Markdown | 严格 UTF-8 文本提取，拒绝无效编码和 NUL 字符 |
| DOCX | 校验 ZIP 结构及展开大小后，用 Mammoth 提取正文，不执行宏或输出文档 HTML |
| 文字 PDF | 使用 Poppler 检查页数、加密状态并逐页提取文字 |
| 扫描 PDF | 某页有效文字少于 20 字符时，将该页渲染为图片后调用视觉模型转录 |
| PNG、JPG／JPEG、WebP | 解码校验后缩放至不超过 2000 × 2000，调用视觉模型转录；拒绝多帧图片及超过 2000 万像素的输入 |

限制为每文件 10 MiB、PDF 30 页、全库 300 份文档、原文件合计 256 MiB；单份正文提取或编辑最多 100 万字符，单文档切分最多 6000 个。另有全库默认5000个分段／64 MiB向量预算，包含草稿及保留的旧版本，索引前和事务落库时均检查。超限会明确报错并保留原发布版本，不会静默截断或自动删除资料；已有超额库仍可检索，需先核对容量再索引新版本。加密、损坏或无法提取有效正文的文件不能发布。

处理状态为 `queued → extracting → indexing → draft`，失败进入 `failed`；已经保存正文的任务可直接进入 `indexing`。每次仅处理一份文档，解析、Embedding 和余弦计算放在受限子进程；子进程通过 IPC 回传阶段及结果，API 检查文档版本后才写入。进程退出时清理临时文件，重启会重新排队中断阶段。

草稿必须人工发布后才参与顾客检索。编辑已发布文档会生成新版本并重新索引，旧发布版本保持可检索，直到新版本发布或主动停用。发布在一个事务中切换有效版本；旧任务回调不得覆盖新版本、复活已删除或已停用的文档。停用立即取消其公开检索资格，删除会删除原文档及关联分段。失败或停用文档可重试，重试不会自动发布。

正文按段落切分，每段最多约 600 字符，长段落相邻分段重叠约 100 字符，保存页码／段落信息。中文分词与双字组合写入 SQLite FTS5，BM25 关键词结果和向量余弦结果各取 20 条，使用 RRF 合并，再对最多 30 条候选重排，最终最多 6 段进入模型上下文。FAQ 走关键词索引，保存、停用或删除后的有效内容立即更新。

检索以内容指纹去重，向量按64条一批送入排序子进程并合并候选，正文只读取最终融合候选；不会为一次咨询把全库向量和正文同时装入 API 内存。

只有本轮检索得到且仍有效的来源 ID 能写入回答引用。停用、删除或更新来源会再次校验，防止生成期间使用已经失效的引用。原始文件只有具有客服管理权限的后台账号可以下载；顾客看到的是已发布摘录。上传内容应限于可对客提供的说明，不上传个人资料、内部凭据或机密材料：文档正文会发往 Embedding，扫描页／图片会发往视觉模型，选中的检索段落会发往对话与重排服务。

## 工具与业务确认

工具仅包含商品搜索／详情、知识检索、本人近期订单／详情，以及生成三种提案：`addCart`、`cancelOrder`、`requestAfterSale`。身份来自服务端会话，模型或请求体传入的用户 ID 不授予权限；订单工具排除地址、电话、凭据和后台财务字段。商品价格、库存、订单状态及售后申请金额由现有业务规则提供。

模型只生成待确认提案，卡片展示规格、数量、目标订单、售后明细及金额。确认接口只接收提案 ID 和请求标识，不能由客户端替换原提案参数。提案绑定账号与会话，10 分钟过期；确认时重新检查价格、库存、订单和售后状态，变化后要求重新生成。提案消费、业务修改、确认消息及幂等结果在同一事务提交，任何一步失败均回滚。相同提案重复确认返回原结果，不会再次加购或申请售后。

取消待付款订单和申请售后复用原页面的规则；申请售后只是提交待审核申请。没有自动付款、发货、审核通过或执行退款工具。检索资料和用户输入均作为不可信资料；工具名称、参数、最终结构和来源 ID 都经过服务端校验，不执行任意 SQL、代码或 URL 抓取。

## 任务、故障与恢复

每个账号同时只能有一个活跃客服任务，因此同一会话也不会同时生成两轮。默认全局 2 个运行任务加 20 个排队任务，繁忙时返回 429；每轮最多 4 次模型调用、8 次工具执行，从入队起总期限 90 秒。HTTP 发送消息仅在短事务内保存消息、任务和幂等结果，模型请求在事务外执行。

| 情况 | 行为与处理 |
| --- | --- |
| 模型未配置、超时、429／5xx、断网或结构异常 | 保留用户消息，任务失败并给出规则来源的失败提示；修复配置／网络后点击重试或转人工 |
| Embedding 检索故障 | 显示 `embedding_unavailable_keyword_only`，使用关键词结果；文档索引故障则保持失败，不允许发布 |
| Embedding 模型与已存向量不匹配 | 显示 `embedding_model_changed`；重新索引并发布匹配的版本 |
| Reranker 故障或关闭 | 显示 `reranker_unavailable_fusion_order`，使用 RRF 融合顺序 |
| 文档识别或索引失败 | 在管理端查看错误码，确认配置、文件格式和容量；核对可用的提取文本，可修改保存或重试 |
| 用户转人工或会话关闭 | 取消该会话活跃任务及未确认提案，迟到回答不得写入；已完成的业务确认仍保留 |
| API 重启 | 中断的客服任务重新排队，保留调用计数和总期限；文档中断阶段重新处理。已经落库的回答不重复追加 |
| 用户明确重试失败客服任务 | 重新分配本轮期限与调用预算，旧未确认提案取消，新的提案需要重新确认 |

重启恢复不保证外部供应商“恰好调用一次”：进程可能在供应商已返回、业务结果尚未落库时退出，再次请求可能重复计费。当前部署仍为单 API 实例，不支持多个实例同时消费这些任务。

运行时可在 `docker compose logs --tail 100 api` 中按 `runId` 关联 `support_model_call`、`support_run_failed` 等事件，查看调用编号、固定错误码及供应商返回用量；HTTP 请求日志另含请求耗时。日志不输出完整提示词、原始文档、模型响应正文或 Key。完整输出不要附带 `.env` 或未经脱敏的数据库。

## 接口与持久化

以下接口沿用现有 Cookie 认证、`X-ShopMate-Request: 1` 写入标识、访问源校验与权限约定：

| 接口 | 内容 |
| --- | --- |
| `GET /api/support/config` | 读取 `aiEnabled`，不包含凭据 |
| `GET /api/support/conversations/:id` | 本人会话、最新任务、提案和关联商品／本人订单；不依赖列表当前页 |
| `POST /api/actions/sendMessage` | 原参数 `[conversationId, text]`，顶层传 `requestId` |
| `POST /api/actions/retrySupportRun` | 参数 `[runId]`，顶层传 `requestId` |
| `POST /api/actions/confirmSupportProposal`、`cancelSupportProposal` | 参数 `[proposalId]`，顶层传 `requestId` |
| `GET /api/support/documents`、`/:id`、`/:id/file` | 具有客服管理权限的账号读取列表、提取结果及原始文件 |
| `POST /api/support/documents` | JSON 中传 `name`、`contentBase64`、`requestId`，原文件上限 10 MiB，传输 JSON 上限 15 MiB |
| `POST /api/support/documents/:id/actions` | `action` 为 `save/publish/disable/delete/retry`，携带当前 `version`、`requestId`；`save` 另带 `text` |

文档操作按管理账号和请求标识幂等，旧版本冲突返回 409。客服确认沿用已有业务命令的账号／方法／请求标识幂等，提案本身另有消费状态保护。

新增 SQLite 表为 `support_runs`、`support_tool_calls`、`support_proposals`、`ai_documents`、`ai_knowledge_chunks`、`ai_knowledge_faqs`、`ai_knowledge_requests` 及派生的 `ai_knowledge_fts`。原始文档 BLOB、提取正文、向量、任务和提案都保存在同一数据库，无需额外备份上传目录。迁移为新增表，不改旧业务状态版本。

备份清单继续使用格式 1，增加可选 `digests.ai` 和普通 AI 表的行数；按行处理文档 BLOB 与向量，SQLite 文件校验使用分块 SHA-256，FTS 虚拟表／派生影子表不重复纳入 AI 行摘要。旧清单仍可检查。升级前一致备份、保留数据卷和离线恢复流程见 [可靠性与运维](reliability.md)；恢复后应核对文档发布版本、任务状态及已消费提案，不能只检查首页健康。

## 测试与证据边界

确定性回归使用模拟模型与合成资料，不需要真实 Key；测试入口沿用 [开发文档](development.md#验证命令)。PDF 解析用例调用真实 Poppler，并模拟视觉响应；Windows 缺少 `pdftotext` 时该用例会明确跳过，应在安装完整 Poppler 的 CI 或隔离容器中补跑，不能把跳过计为 PDF 验证通过。

真实供应商验收脚本为 `backend/scripts/ai-acceptance.mjs`，合成格式样例位于 `backend/test/fixtures/ai/`。脚本创建测试账号、文档和交易并产生模型费用，只允许显式授权的独立本机端口，拒绝日常 18086 端口。运行前使用独立 Compose 项目、镜像、端口和数据卷，关闭日常备份路径绑定；保存报告并逐项核对来源、金额、否定语句和操作结果。自动测试、供应商正常联调与故障降级分别记录，不能相互替代，也不说明长期准确率或稳定性。
