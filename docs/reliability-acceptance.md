# 单店电商 v4 交付验收

本轮按单店、单仓、单 API 进程实施。交易仍使用模拟支付、退款与物流；以下测试不代表长期运行保证，也不推导多实例容量。

## 实现与审查

业务 JSON 已迁移为按领域、按记录的 SQLite 表，保留不可改写的旧 JSON 证据。金额快照、账号和会话、旧订单库存规则不重建。新客户端使用身份初始化、分领域查询和 SQL 筛选分页；兼容全量读取接口仍标记弃用。写请求默认必须有请求标识，商品和配置修改校验版本；仅旧测试夹具显式启用无标识兼容模式。

新功能覆盖配送运费、满减择优、积分与退款冲回、供应商与分批采购入库、退货隔离和质检、五类员工权限、本人通知、财务差异核对、操作审计、持久化任务以及一致备份恢复。具体规则见 [经营规则](commerce-v4.md)，故障处置见 [运维手册](reliability.md)。

浏览器回归同时检查了原有商品、购物车、优惠券、交易履约、售后、评价及人工客服。发现的问题包括分页数据误当全量计数、已领券模板超出初始化上限、待评价上下文遗漏、身份切换后的表单草稿、购买直达结算和流水关联上下文；均作为回归项处理。

## 负载与故障方法

通过独立 Compose 项目、镜像标签、端口和数据卷执行。小数据集和 1 万笔已完成历史订单各以 50 个并发请求持续 600 秒；负载为 90% 商品／本人订单分页／积分读取，10% 带幂等键的购物车选择写入，不等于每秒同等数量的下单或付款。

最终复测沿用各自隔离数据卷，保留前序调优产生的幂等记录；“小数据集”指 0 笔历史订单，并非所有表为空。压测后的只读报告列出实际命令记录数量，逐项比较种子商品、订单、库存及流水摘要，并核对每个 SKU 的库存变动、预占和关系表投影。万笔历史订单及逐笔收款是合成数据，不能当作真实支付证据。

记录吞吐、P95/P99、HTTP 状态、资源采样及镜像源码摘要。50 人热点库存竞争、付款／退款重复提交、响应丢失、进程被终止、未提交事务回滚、数据库锁竞争、认证过载及恢复后守恒另行演练。数据库锁通过独立维护进程持锁测试，服务返回可识别的 503，再以原请求标识重试；这与正常单进程串行写入的锁等待不同。

曾出现多次未达门槛的中间版本结果，保留为诊断依据：

- 上游短连接造成临时端口耗尽，316982 个请求中出现 85699 个 502。修复为 Nginx HTTP/1.1 上游连接复用及空闲超时配合。
- 1 万历史订单版本中，购物车库存检查加载并差分保存买家的全部历史订单，32845 个请求中出现 9 个 504，P95 1876 ms、P99 2910 ms。改为读取全局有效预占与本命令明确关联的历史订单，专项测试证明 1 万笔历史订单不被解析或重写。
- 收窄写事务后，大数据复测仍出现 504，已提前停止，不计通过。进一步通过 SQLite `EXPLAIN QUERY PLAN` 确认：万笔订单时间戳相同，旧索引缺少末尾 ID 排序键，分页仍需读取全量记录并临时排序。补齐所属用户／状态／时间／ID 的复合分页索引，已有库启动时同样增建；查询计划回归禁止该分页使用临时排序。

## 运行和交付边界

测试主机使用 Windows 的 Docker Desktop Linux 引擎，分配 12 个逻辑 CPU、约 15.2 GiB 内存；API 单容器上限 1 GiB。共享开发主机的测量不能外推到其他硬件。源码摘要对运行镜像中的 `backend/src`、`shared` 和后端包清单排序、统一 LF 后计算，代理配置另存 SHA-256；部署时重新核对摘要及 Git 镜像版本标签。

日常环境只执行健康、公开页面、挂载、版本和数据摘要核对，不创建验收交易。升级前保留数据库一致备份、清单、旧镜像和配置；备份、凭据及数据库不提交 Git。备份恢复能够验证指定故障路径，不覆盖真实磁盘损坏、整机丢失、持续数周运行或真实外部服务故障。
